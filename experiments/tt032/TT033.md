# TT-033: one compiled restoration candidate

Authoritative task: [TT-033 / issue 27](https://github.com/DanMarshall909/TurboTest/issues/27).
This is an isolated feasibility experiment. TT-032's measured checkpoints and
archives remain historical evidence. Production code is unchanged.

## Frozen question and contract

Can a cached SQL restoration command with bounded connection reuse take no more
than half the complete warm time of matched Respawn for 1,000 tests / four workers?
Use the existing workload, seeds, independent baseline/result assertions, four
database slots, four restoration workers, at most four workload connections per
database, 256 MiB PostgreSQL container, digest-pinned PostgreSQL 16 image and
native Linux host. Keep shared-host load observations. No hardware exclusivity,
WSL2, native Windows, crash-durability or product-wide speed claim is made.

Both contenders prepare under durable settings, then disable fsync,
synchronous_commit and full_page_writes together; count that transition in
preparation. Use the existing 15 s SQL deadline and full cleanup accounting.
Four warmup cycles precede 1,000 recorded cycles. The primary metric is SuiteMs:
first request through all returns, replenishment and exact final capacity audit.
Retain preparation, warmup, process wall, resource observations and final drain
separately; do not add overlapping component intervals or compare only return
latency. The warm-service claim excludes its separately reported destruction.

The candidate's plan is generated/cached SQL text, **not a server-prepared query**.
The fixed workload declares its dependency order and deterministic seed input.
One command executes BEGIN, child-to-parent DELETEs, parent-to-child seed INSERTs,
exact setval calls and COMMIT. This is a workload-specific prototype, not a
generic schema/seed compiler. Plan construction and retained UTF-8 byte size are
recorded during preparation. Workload and restoration use the same bounded source.
SchemaVersion is immutable, matching the reference's declared exclusion.

The common contract is fixed-schema data restoration with explicit schema
invalidation and native replacement. The candidate does not implement TurboTest's
automatic catalog-change detection. Every reset failure remains recorded; a
failed slot is quarantined, its source disposed, and its database replaced before
publication. Failure to replace fails admission/drain. Unexpected recovered
failures, including warmups, disqualify a performance run.

Qualification uses the shared real PostgreSQL probes for both contenders under
relaxed settings, including a fresh fixture after server loss. Both must show
bounded physical connection reuse. The candidate additionally injects a named
runtime error after setting a sequence to 9001, observes that value after
ROLLBACK, proves old OID/backend removal, and exercises the replacement slot.
This deliberate fault is qualification evidence and cannot make an ordinary
performance failure eligible.

## Measurement and decision fixed before timing

One candidate and five independent pairs. Round 0 starts with Respawn; subsequent
rounds alternate order. Each case starts a new process/container. No automatic
retry and no selecting a variant after seeing representative results. A failed
case remains in the result; source/binary drift or missing cleanup stops the
affected phase. Qualification must pass at the exact representative source and
binary identity first. Every receipt binds plan, command, environment, report
digest, images, source and binary, before/after load and Docker inventory.

The comparison statistic is candidate median SuiteMs / reference median SuiteMs.
Enumerate all 5^5 paired bootstrap resamples, preserving each round's pair, and
report the nearest-rank 2.5% and 97.5% quantiles. Five pairs support only a small
local experiment, not a hardware-population guarantee. Success requires every
qualification and cleanup check, all ten representative runs successful, and
the upper ratio bound <= 0.5. The earlier 3.233 s number is a planning reference;
the new contemporaneous paired reference determines the measured threshold.

Report raw run values, median, p95/max, pooled descriptive operation tails,
resource/disk observations and source/cleanup evidence. Individual cycles are
not independent suite replicates. If the threshold is missed, publish that
negative result and stop this candidate; no further tuning series is authorized.
Keep adopting Respawn, revising the mechanism or deferring as explicit decisions.

## Reproduce

From a clean committed checkout with the recorded SDK, restored lockfile and
cached digest-pinned image, use new output paths and the explicit Docker daemon:

```sh
dotnet build experiments/tt032/CompetitiveBaseline.csproj -c Release --no-restore
python3 experiments/tt032/tools/run_compiled.py qualify --output artifacts/tt033/qualification
python3 experiments/tt032/tools/run_compiled.py paired --qualification artifacts/tt033/qualification --output artifacts/tt033/paired
python3 experiments/tt032/tools/analyze_compiled.py artifacts/tt033/paired --output artifacts/tt033/summary.json
```

The supervisor does not rebuild between cases. Preserve every failed attempt and
use a new explicit attempt path after any required qualification repair.
